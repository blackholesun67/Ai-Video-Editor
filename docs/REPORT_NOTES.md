## บทที่ 1 — บทนำ

### 1.1 ชื่อโครงงาน

**ระบบตัดต่ออัตโนมัติ ด้วยปัญญาประดิษฐ์วิเคราะห์ภาพและเสียง**
(AI Video Smart Editor — Automated video editing with AI analysis of image and audio)

### 1.2 ที่มาและความสำคัญ

การตัดต่อวิดีโอมีงานซ้ำซากที่กินเวลามากแต่ไม่ต้องใช้ความคิดสร้างสรรค์ คือการ **ไล่หาช่วงที่ต้องตัดทิ้ง**
— ช่วงเงียบ ช่วงพูดผิดแล้วพูดใหม่ คำติดปาก ("อืม" "เอ่อ") ปัญหาเทคนิค — ซึ่งคนตัดต่อต้องนั่งดูคลิป
ทั้งเรื่องเพื่อหาจุดเหล่านี้ คลิป 1 ชั่วโมงอาจใช้เวลาไล่หาหลายชั่วโมง

ระบบนี้ให้ AI ทำขั้น "ไล่หา" แทน แล้ว **คืนการตัดสินใจขั้นสุดท้ายให้คน** ผ่านหน้าตรวจสอบที่แก้ไขได้จริง

### 1.3 วัตถุประสงค์

1. พัฒนาระบบที่ถอดเสียงพูดในวิดีโอแล้ววิเคราะห์เพื่อระบุช่วงที่ควรตัดออกโดยอัตโนมัติ
2. นำ **ข้อมูลจากภาพ** มาร่วมตัดสินใจ ไม่ใช่วิเคราะห์จากเสียงเพียงอย่างเดียว
3. สร้างคำบรรยาย (subtitle) ภาษาไทยที่ตรงกับจังหวะการพูดจริง และแก้ไขได้ก่อนนำไปใช้
4. ออกแบบส่วนติดต่อผู้ใช้ที่ให้คนตรวจสอบและปรับแก้ผลของ AI ได้ก่อนตัดต่อจริง
5. รองรับผลลัพธ์ทั้งแนวนอน 16:9 และแนวตั้ง 9:16

### 1.4 ขอบเขต

**ทำได้**

- วิดีโอ `.mp4 .mov .mkv .avi .webm .m4v` ขนาดไม่เกิน 2 GB
- ภาษาไทยเป็นหลัก รองรับภาษาอังกฤษที่แทรกอยู่ (แปลเป็นไทยอัตโนมัติได้)
- ตัดต่อ + ต่อคลิป + ฝังคำบรรยาย + แปลงสัดส่วนเป็น 9:16
- ทำงานบนเครื่องเดียว (single-node) ผ่าน Docker

**ไม่ครอบคลุม**

- การตัดต่อเชิงสร้างสรรค์ (เลือกมุมกล้อง จังหวะดนตรี เอฟเฟกต์ทรานซิชัน)
- ระบบผู้ใช้หลายคน / การยืนยันตัวตน / ฐานข้อมูล (เก็บงานเป็นไฟล์ ลบอัตโนมัติใน 7 วัน)
- การประมวลผลแบบเรียลไทม์หรือสตรีมมิ่ง
- ภาษาอื่นนอกจากไทย-อังกฤษ

### 1.5 ประโยชน์ที่คาดว่าจะได้รับ

ลดเวลาขั้นตอน "ไล่หาช่วงที่ต้องตัด" · ได้คำบรรยายไทยที่ตรงจังหวะพูดโดยไม่ต้องพิมพ์เอง ·
ผู้ใช้ยังควบคุมผลลัพธ์ได้เต็มที่เพราะ AI เสนอ ไม่ได้ตัดสินแทน

## บทที่ 2 — ทฤษฎีและเทคโนโลยีที่เกี่ยวข้อง

### 2.1 Automatic Speech Recognition — Whisper

**Whisper** (OpenAI) เป็นโมเดล ASR สถาปัตยกรรม encoder–decoder Transformer ทำงานแบบ
**autoregressive** คือทำนายโทเคนถัดไปจากเสียง *และจากโทเคนที่ตัวเองสร้างไปแล้ว*
โปรเจกต์ใช้ **faster-whisper 1.2.1** ซึ่ง implement ด้วย CTranslate2 (เร็วกว่า/กิน VRAM น้อยกว่า)

คุณสมบัติที่โปรเจกต์ใช้:

- **word-level timestamps** — เวลาระดับคำ ได้จาก forced-alignment บน cross-attention
- **BatchedInferencePipeline** — ประมวลผลหลายช่วงขนานกัน เร็วขึ้น 3–4 เท่า
- **temperature fallback** — ถ้า decode รอบแรกได้ผลผิดปกติ จะ decode ใหม่ที่ temperature สูงขึ้น
- `avg_logprob` / `no_speech_prob` — ค่าความมั่นใจของโมเดลต่อผลลัพธ์แต่ละท่อน

**ข้อจำกัดที่พบและต้องรับมือ** (สำคัญมากสำหรับบทที่ 4)

1. *timestamp ระดับ segment ไม่น่าเชื่อถือ* — Whisper ยืด `end` ของแต่ละ segment ให้ชนกับ
   `start` ของ segment ถัดไป ทำให้ช่องว่างระหว่าง segment เกือบเป็นศูนย์เสมอ แม้ผู้พูดจะหยุดจริง
   → ถ้าจะวัดความเงียบหรือหาจุดจบประโยค ต้องใช้ timestamp ระดับคำเท่านั้น
2. *Whisper segment ไม่เท่ากับประโยค* — วัดจาก 519 ท่อน: p50 = 2.66 วิ แต่ **p75 = 11.26 วิ,
   p90 = 20.26 วิ, สูงสุด 31.49 วิ** เพราะโมเดลรวมหลายประโยคไว้ในหน้าต่างเดียว
3. *repetition loop (การหลอน)* — ดูหัวข้อ 4.2

### 2.2 Voice Activity Detection — Silero VAD

โมเดลขนาดเล็ก (PyTorch) แยก "ช่วงที่มีเสียงพูด" ออกจาก "ช่วงที่ไม่มี" ใช้ใน 2 บทบาท:

1. กรอง segment ที่ไม่มีเสียงพูดออกก่อนส่งให้ LLM (ลดโทเคน ลดการหลอน)
2. **แยกเสียงพูดออกจากดนตรี** — ดนตรีบรรเลงไม่ถูกนับเป็นเสียงพูด ใช้หาว่า "เสียงพูดจบตรงไหน"
   เพื่อไม่ให้ระบบคืนหางเพลงท้ายคลิปกลับมา

### 2.3 Large Language Model — Google Gemini

ใช้ Gemini (`gemini-2.5-flash` และ `gemini-3.6-flash` เป็น fallback chain) ใน 3 หน้าที่:

1. **แก้ทรานสคริปต์** — ชื่อเฉพาะ ศัพท์เทคนิค และแปลประโยคอังกฤษที่แทรกเป็นไทย
2. **ตัดสินใจว่าช่วงไหนควรลบ** — งานหลัก
3. **ร่างโครงเรื่อง (outline)** — เฉพาะโหมดสรุป ใช้ตรวจย้อนหลังว่าประเด็นหลักไม่หาย

Gemini เป็นโมเดล **multimodal** จึงรับภาพได้ — โปรเจกต์ใช้ความสามารถนี้ส่งคีย์เฟรมไปให้ดูด้วย
(หัวข้อ 3.5) ซึ่งเป็นสิ่งที่ทำให้ระบบ "วิเคราะห์ภาพ" ได้ตามชื่อโครงงาน

### 2.4 การประมวลผลวิดีโอ — FFmpeg

- `filter_complex` — ตัด (`trim`) + ต่อ (`concat`) + ปรับขนาด + ฝังซับ **ใน pass เดียว**
  ทำให้ได้ความแม่นระดับเฟรมและไม่เกิดการเลื่อนสะสมของเสียง
- ตัวตรวจจับจากภาพ: `scdet` (ฉากเปลี่ยน), `blackdetect` (จอดำ), `freezedetect` (ภาพค้าง)
- `boxblur` + `overlay` — ทำพื้นหลังเบลอสำหรับแปลงคลิปไวด์เป็น 9:16
- เวอร์ชันในคอนเทนเนอร์คือ **4.4.2** (Ubuntu 22.04) จึง **ไม่มี** `blurdetect` (ต้องใช้ 5.0 ขึ้นไป)

### 2.5 การตัดคำภาษาไทย — PyThaiNLP

ภาษาไทยไม่เว้นวรรคระหว่างคำ การขึ้นบรรทัดซับจึงต้องตัดคำก่อน ใช้ `newmm`
(Maximum Matching + TCC) และมีตรรกะเพิ่มไม่ให้ตัดกลางพยางค์ เช่นห้ามขึ้นบรรทัดใหม่
ด้วยสระตาม (ะ า ำ ๅ) ไม้ยมก (ๆ) หรือวรรณยุกต์

### 2.6 สถาปัตยกรรมซอฟต์แวร์ที่ใช้

Docker Compose (4 container) · FastAPI (REST API) · Celery + Redis (คิวงานเบื้องหลัง) ·
React 19 + Vite + Tailwind CSS (หน้าเว็บ) · NVIDIA CUDA 12.4 (เร่งความเร็ว Whisper)

## บทที่ 3 — การออกแบบและพัฒนาระบบ

### 3.1 ภาพรวมสถาปัตยกรรม

```
ผู้ใช้ ──► Frontend (React, พอร์ต 80)
              │ HTTP/JSON
              ▼
         Backend API (FastAPI, พอร์ต 8000)  ── จำกัด RAM 1 GB
              │ ส่งงานเข้าคิว
              ▼
         Redis (broker) ──► Celery Worker ── จำกัด RAM 5 GB + ใช้ GPU
                                  │
                                  ├─ FFmpeg (ตัด/ต่อ/ซับ/วิเคราะห์ภาพ)
                                  ├─ Whisper + Silero VAD (GPU)
                                  └─ Gemini API (ผ่านอินเทอร์เน็ต)
```

**เหตุผลที่แยก API ออกจาก Worker**: งานถอดเสียงและตัดต่อใช้เวลาหลายนาที ถ้าทำใน request
จะ timeout และบล็อกผู้ใช้คนอื่น · แยกแล้วยังจำกัดหน่วยความจำแยกกันได้ (การโหลด Whisper
ในคอนเทนเนอร์ API ที่จำกัด 1 GB จะถูกระบบ kill ทันที)

### 3.2 ขั้นตอนการทำงาน (pipeline)

| ขั้น | ทำอะไร | เครื่องมือ |
|---|---|---|
| 1 | สกัดเสียง + ปรับความดัง + ลดเสียงรบกวน | FFmpeg (`loudnorm`, `afftdn`) |
| 2 | ตรวจช่วงที่มีเสียงพูด | Silero VAD |
| 2b | **วิเคราะห์ภาพ** — ฉากเปลี่ยน/จอดำ/ภาพค้าง | FFmpeg (pass เดียว) |
| 3 | ถอดเสียงรอบหลัก | Whisper (batched) |
| 4 | ถอดซ้ำเฉพาะช่องว่างที่ยาวเกิน 5 วินาที | Whisper (non-batched) |
| 4b | **ตรวจและซ่อมท่อนที่หลอน** | Whisper + เกณฑ์เชิงสถิติ |
| 5 | แก้คำผิด **ขนานกับ** ตัดสินใจว่าจะลบช่วงไหน | Gemini สองคำขอพร้อมกัน |
| 6 | **guard 4 ชั้น** ตรวจสอบผลของ AI | โค้ด Python |
| 7 | สร้างวรรคคำบรรยาย | PyThaiNLP + timestamp ระดับคำ |
| 8 | ผู้ใช้ตรวจ/แก้ในหน้าเว็บ | React |
| 9 | ตัด + ต่อ + ฝังซับ | FFmpeg (`filter_complex`) |

### 3.3 หลักการออกแบบสำคัญ: ระบบเป็นแบบ deletion-based

ระบบ **ไม่ได้** ถาม AI ว่า "ช่วงไหนควรเก็บ" แต่ถามว่า **"ช่วงไหนควรลบ"** แล้วโค้ดพลิกกลับเอง

**เหตุผล**: ถ้าถามว่า "เก็บอะไร" สิ่งที่ AI ลืมพูดถึงจะ **หายไป** แต่ถ้าถามว่า "ลบอะไร"
สิ่งที่ AI ลืมพูดถึงจะ **ถูกเก็บไว้** — ความผิดพลาดของ AI จึงเอนไปทางปลอดภัยโดยโครงสร้าง

### 3.4 บทเรียนหลัก: คำสั่งในพรอมป์อย่างเดียวเชื่อไม่ได้

นี่คือข้อค้นพบเชิงวิศวกรรมที่สำคัญที่สุดของโครงงาน และควรเป็นแกนของบทที่ 4–5

เมื่อพบว่าโหมดสรุปตัดเนื้อหาสำคัญหาย ความพยายามแรกคือ **เขียนกฎในพรอมป์ให้ชัดขึ้น**
ผลคือ **เนื้อหายังหายเหมือนเดิม** ผู้ใช้รายงานกลับมาว่า "การนอนยังหายอยู่" ทางที่ได้ผลจริง
คือเพิ่ม **การตรวจสอบเชิงโครงสร้างในโค้ด** ที่ไม่ขึ้นกับว่า AI จะเชื่อฟังหรือไม่ เกิดเป็น guard 4 ชั้น:

| Guard | ตรวจอะไร | ทำอะไรเมื่อไม่ผ่าน |
|---|---|---|
| ตรวจความครบของประเด็น | ประเด็นหลักที่ AI ร่างไว้เอง ยังอยู่ครบไหม | คืนช่วงที่หายกลับ |
| ป้องกันคลิปจบห้วน | คลิปจบถึงจุดที่เสียงพูดจบจริงไหม | คืนช่วงท้ายกลับ |
| จัดขอบให้จบประโยค | ขอบตัดตกกลางคำ/กลางประโยคไหม | ขยับขอบออก (ขยายอย่างเดียว ไม่หดเข้า) |
| ปิดท้ายให้จบความ | ประโยคสุดท้ายพูดจบไหม | ยืดจนจบประโยค |

**ข้อควรระวังที่ตามมา (บทเรียนที่ 2)**: guard ที่ทำงานบ่อยเกินไปสร้างความเสียหายมากกว่า
ปัญหาที่มันแก้ — ดูกรณีศึกษาในหัวข้อ 4.5

### 3.5 การวิเคราะห์ภาพ (ส่วนที่ตอบชื่อโครงงาน)

แบ่งเป็น 2 ระดับ:

**ระดับ 1 — สัญญาณเชิงกลไกจาก FFmpeg**
รัน pass เดียว ย่อภาพเหลือ 320 px แล้วอ่าน 3 สัญญาณ: จุดฉากเปลี่ยน, ช่วงจอดำ, ช่วงภาพค้าง
ใช้เวลาประมาณ 14 วินาทีต่อคลิป 7–11 นาที ผลถูกส่งไป **แสดงเป็นขีดบนไทม์ไลน์ให้ผู้ใช้เห็น**
(เจตนา: ไม่นำไปขยับขอบตัดโดยอัตโนมัติ ดูเหตุผลในหัวข้อ 4.5)

**ระดับ 2 — ส่งภาพให้ AI ดู**
เลือกคีย์เฟรมจากจุดฉากเปลี่ยนบวกกับจุดที่กระจายทั่วคลิป (สูงสุด 20 ภาพ กว้าง 512 px)
แนบป้ายเวลากำกับทุกภาพ แล้วส่งไปพร้อมทรานสคริปต์ตอนให้ Gemini ตัดสินใจ
ทำให้ AI เห็นสิ่งที่ทรานสคริปต์บอกไม่ได้ เช่น การ์ดปิดท้าย สไลด์ที่กำลังอธิบาย ภาพเสีย

> การแนบป้ายเวลาจำเป็นมาก — ถ้าไม่มี AI จะรู้แค่ว่า "มีภาพเหล่านี้อยู่ในคลิป"
> แต่ผูกภาพเข้ากับช่วงเวลาในทรานสคริปต์ไม่ได้

### 3.6 หน้าตรวจสอบและแก้ไข (human-in-the-loop)

จุดที่ทำให้ระบบใช้งานได้จริง — ผู้ใช้เห็นและแก้ทุกอย่างก่อนตัดจริง

- เห็นทั้งช่วงที่ AI เก็บ **และช่วงที่ AI ตัดออก** กดเอากลับมาได้
- ขยับขอบทีละ 1 วิ / 5 วิ / 15 วิ / 1 นาที พร้อมเล่นให้ฟังรอยตัดโดยอัตโนมัติ
- **แยกช่วง** ตรงตำแหน่งที่เล่นอยู่ และ **รวมกลับ** ได้ถ้าเปลี่ยนใจ
- แถบไทม์ไลน์แสดงโครงสร้างทั้งคลิปพร้อมขีดจุดฉากเปลี่ยน
- แก้คำบรรยายทีละบรรทัด เฉพาะช่วงที่เลือกไว้จริง

**กฎเชิงโครงสร้างของหน้านี้**: แถวทั้งหมด **ปูเต็มช่วงเวลา [0, ความยาวคลิป] ต่อกันสนิท**
ขอบภายในทุกจุดจึงถูกใช้ร่วมกันโดยแถวสองแถวพอดี การขยับขอบจะขยับทั้งคู่พร้อมกัน
จึง **พิสูจน์ได้เชิงโครงสร้างว่าไม่มีทางเกิดช่องโหว่หรือช่วงทับซ้อน** โดยไม่ต้องตรวจภายหลัง

อีกกฎหนึ่ง: **การแยกช่วงต้องไม่เปลี่ยนผลลัพธ์ที่ได้** — แยกแล้วสั่งตัดทันที ต้องได้ไฟล์เหมือนเดิมเป๊ะ
(มีชุดทดสอบครอบข้อนี้ไว้ 20 กรณี)

### 4.2 การตรวจจับและซ่อมท่อนที่ Whisper หลอน

**ปรากฏการณ์ที่พบ**: ช่วง 29 วินาทีหนึ่งได้ผลถอดเสียงเป็น word token 179 ตัวที่เป็นคำว่า
"หลับ" ซ้ำประมาณ 58 รอบ ขณะที่ข้อความของ segment ยุบเหลือคำเดียวคือ "เทสโทสเตอโรน"
เนื้อหาจริง (โกรทฮอร์โมนหลั่งช่วงต้นของการนอน) หายทั้งท่อน

**พิสูจน์ว่าไม่ใช่ช่วงเงียบ**: วัดระดับเสียงได้ **-20.0 dB ซึ่งเท่ากับช่วงที่ถอดได้ปกติ (-19.8 dB)**
จึงสรุปได้ว่าเป็นความล้มเหลวของการถอดเสียงล้วน ๆ ไม่ใช่เพราะไม่มีเสียง

**การหาเกณฑ์ตรวจจับ** (วัดจาก 3,073 segment)

| ตัวชี้วัดที่ลอง | ผล |
|---|---|
| unique-token ratio | **ใช้ไม่ได้** — p1 ของเนื้อหาปกติอยู่ที่ 0.143 เพราะ token ไทยเป็นเศษพยางค์ ซ้ำกันเป็นปกติ |
| **loop ratio** (หน่วยเดิมซ้ำ **ติดกัน** ตั้งแต่ 3 รอบขึ้นไป) | **ใช้ได้** — เนื้อหาจริงสูงสุด 0.61 · ท่อนที่หลอนต่ำสุด 0.76 → ตั้งเกณฑ์ **0.70** |
| **จำนวนตัวอักษรต่อวินาที** | **ใช้ได้** — ค่ากลางของจริง 13.7 · ต่ำสุดที่ยังเป็นของจริง 3.3 → ตั้งเกณฑ์ **2.0** |

ผลการตรวจจับ: จับได้ **24 เคส** และไม่มีการจับเนื้อหาที่ดีผิดแม้แต่รายการเดียว

**การซ่อม** — ค่าพารามิเตอร์มาจากการทดลองเปรียบเทียบ ไม่ใช่การเดา

| พารามิเตอร์ | ผลที่วัดได้ |
|---|---|
| การระบุภาษา | ให้ตรวจอัตโนมัติ → **ได้ 0 ท่อน** · ระบุ "th" → **ได้ 9 ท่อน** |
| `repetition_penalty = 1.15` | ไม่ใส่ → 2 ท่อนอ่านไม่ออก · ใส่ → **10 ท่อนที่มีเนื้อหา** |
| `no_repeat_ngram_size`, `hallucination_silence_threshold` | **ห้ามใช้** — กดผลจนเหลือศูนย์ (n-gram ไทยซ้ำกันเป็นเรื่องปกติ) |
| `avg_logprob` (ด่านรับผล) | อ่านไม่ออก **-2.5** · ได้ใจความ **-1.4** · ชัดเจน **-0.25** → ตั้งเกณฑ์ **-2.0** |

**ผลลัพธ์**: ท่อนที่เคยได้คำบรรยาย 1 บรรทัดค้างบนจอ 29 วินาที กลายเป็น **12 ท่อนที่ได้ใจความ**
เช่น "โกรทฮอร์โมน...ช่วงต้นของการนอน", "ช่วยฟื้นฟูกล้ามเนื้อ", "ตัวสุดท้ายคืออินซูลิน"

### 4.3 ผลของการให้ AI เห็นภาพ (การทดลองแบบ A/B)

รันงานเดิมสองครั้งโดยเปิด/ปิดการส่งคีย์เฟรม และปิดการแก้ทรานสคริปต์เพื่อตัดตัวแปรอื่นออก

**กรณีที่ 1 — คลิปฟิตเนส 7 นาที (ภาพช่วยชัดเจน)**

| ช่วง | วิเคราะห์จากเสียงล้วน | เมื่อเห็นภาพด้วย |
|---|---|---|
| 381.6–394.7 วิ (คำเชิญชวน/ช่องทางติดต่อ) | **ตัดทิ้ง** โดยให้เหตุผลว่าไม่ใช่เนื้อหาหลัก | **เก็บไว้** |
| 394.7–417.1 วิ | เดาว่าเป็น "ความเงียบหรือเสียงดนตรียาว" | ระบุถูกว่าเป็น **"การ์ดปิดท้ายแสดงช่องทางติดต่อ"** |

การวิเคราะห์จากเสียงล้วนได้ยินแค่ "เงียบ" จึงเดาว่าเป็นเพลง และเผลอตัดคำเชิญชวนก่อนหน้าทิ้งไปด้วย

**กรณีที่ 2 — คลิปนำเสนอ 6 นาที (ผลก้ำกึ่ง)**
เมื่อเห็นภาพ ระบบตัดช่วงปัญหาเทคนิคเป็นก้อนเดียวได้สะอาดกว่า (เสียงล้วนทิ้งเศษ 4.9 วินาทีค้างไว้)
แต่กลับเก็บคำติดปาก "ออออ" ไว้ 18.8 วินาที ซึ่งแย่กว่า

**สรุปอย่างตรงไปตรงมา: ชนะชัดเจน 1 กรณี ก้ำกึ่ง 1 กรณี** — การให้ AI เห็นภาพช่วยได้จริงเมื่อ
ข้อมูลที่ต้องใช้ตัดสินอยู่ในภาพ (การ์ดปิดท้าย สไลด์) แต่ไม่ใช่วิธีที่ดีขึ้นเสมอไป
จึงออกแบบให้ปิดได้ด้วยตัวแปรสภาพแวดล้อม

### 4.4 การเลือกวิธีแปลงสัดส่วนเป็น 9:16

**ปัญหา**: คลิปสัดส่วน 2.35:1 (1280×544) แปลงเป็น 1080×1920 ด้วยวิธีตัดขอบ (crop)
ต้องขยายภาพ 3.529 เท่าแล้วตัดส่วนล้น → **เหลือความกว้างของต้นฉบับเพียง 24%**

**สมมติฐานแรกที่ตั้งไว้**: ควรทำ face-aware crop คือตรวจจับใบหน้าแล้วเลื่อนกรอบตาม

**การพิสูจน์สมมติฐาน**: สุ่มดู 12 เฟรมพร้อมวาดกรอบ crop ทับ พบว่าเสียหาย 10 เฟรม
แต่ face-aware crop จะแก้ได้เพียง 2 เฟรม

| ประเภทเนื้อหาในเฟรม | จำนวน | face-crop แก้ได้ไหม |
|---|---|---|
| ข้อความเต็มความกว้าง | 5 | ไม่ได้ — ไม่มีกรอบกว้าง 24% ใดเก็บข้อความเต็มบรรทัดได้ |
| ภาพเทียบซ้าย–ขวา | 3 | ไม่ได้ — ต้องเห็นทั้งสองฝั่ง |
| กริดคลิปย่อย / ภาพประกอบที่ไม่มีคน | 2 | ไม่ได้ — ไม่มีใบหน้าให้ตาม |
| คนเดียวอยู่นอกกึ่งกลาง | 2 | ได้ |

**ข้อสรุป**: สมมติฐานแรกผิด วิธีที่ถูกคือ **ย่อทั้งเฟรมให้เห็นครบแล้วเติมขอบด้วยภาพเดิมที่เบลอ**
ซึ่งแก้ได้ทั้ง 12 เฟรม โดยไม่ต้องเพิ่มไลบรารีใด ๆ เลย

> **ข้อสังเกตเชิงระเบียบวิธี**: ข้อค้นพบนี้เกิดจากการ **วัดก่อนลงมือพัฒนา** ถ้าพัฒนา
> face-aware crop ไปเลยตามสมมติฐาน จะเสียเวลากับไลบรารีตรวจจับใบหน้าและการแปลงเวลา
> แล้วได้ผลที่แก้ปัญหาได้เพียง 1 ใน 6 ของเฟรมที่เสียหาย

### 4.5 กรณีศึกษา: กลไกแก้ไขอัตโนมัติที่ทำงานบ่อยเกินไป

**กรณีที่ 1** — กลไกยืดขอบเมื่อ "ยังพูดไม่จบความ" ถูกเพิ่มเพื่อแก้อาการตัดก่อนพูดจบ
ผลคือ **เนื้อหากระโดดทั้งคลิป** เพราะผู้พูดเว้นจังหวะสั้น ๆ ที่เกือบทุกรอยต่อประโยค
กลไกจึงทำงานเกือบทุกจุดแล้วดึงประโยคแรกของช่วงที่ควรลบเข้ามา
→ ปัจจุบัน **ตั้งค่าเริ่มต้นเป็นปิดโดยตั้งใจ**

**กรณีที่ 2** — เพดานการ "กลืนท่อนถอดเสียงให้จบ" เดิมตั้ง 25 วินาทีบนสมมติฐานว่า
1 Whisper segment เท่ากับ 1 ประโยค เมื่อวัดพบว่าสมมติฐานผิด (p75 = 11.26 วิ)
กลไกจึงลากคำติดปากกลับเข้ามา 14.5 วินาที → แก้ให้ผูกกับเพดานเดียวกับการยืดขอบแบบอื่น (6 วินาที)

**การวัดรัศมีผลกระทบก่อนแก้** — บทเรียนเรื่องการเลือกวิธีวัด

| วิธีวัด | ผล | ตีความ |
|---|---|---|
| ขอบสุ่ม 1,080 ช่วง | เปลี่ยน **67.6%** | **หลอกตา** — ขอบสุ่มไม่ใช่ตัวแทนของขอบที่ AI เลือกจริง |
| ชุดตัดจริงจาก log 4 ชุด (17 ขอบ) | เปลี่ยน **1 ขอบ** | และคือบั๊กที่ต้องแก้พอดี |
| ช่วงที่บันทึกไว้ 9 งาน | **ไม่ขยับเลย** | ไม่กระทบผลที่ถูกต้องอยู่แล้ว |

### 4.6 บั๊กจากการปนโดเมนเวลา

**บั๊กที่ 1 — ไฟล์ผลลัพธ์ยาวเกินตัวเลขที่แสดงบนหน้าจอ**
ระบบบวกเวลาเผื่อท้ายช่วง 0.2 วินาทีเพื่อกันเสียงขาด แต่บวกกับขอบที่ **ผู้ใช้ตั้งเอง** ด้วย
ทั้งที่ขอบนั้นเป็นตำแหน่งที่ตั้งใจเลือกและผู้ใช้เห็นตัวเลขแล้วกดยืนยันมา

| งาน | จำนวนช่วง | สั่งตัด | ได้จริง | เกิน |
|---|---|---|---|---|
| A | 2 | 387.30 วิ | 387.68 วิ | +0.38 วิ |
| B | 2 | 373.90 วิ | 374.37 วิ | +0.47 วิ |
| C | 1 | 135.70 วิ | 135.93 วิ | +0.23 วิ |

**บั๊กที่ 2 — คำบรรยายเลื่อนจากภาพ** (พบระหว่างแก้บั๊กแรก)
วิดีโอถูกตัดด้วยขอบที่บวกเวลาเผื่อแล้ว แต่คำบรรยายคำนวณตำแหน่งจากขอบที่ยังไม่บวก
→ 2 ช่วงเลื่อน 0.20 วิ · 3 ช่วง 0.40 วิ · **4 ช่วง 0.60 วิ** ซึ่งเห็นได้ด้วยตา

แก้ทั้งสองพร้อมกันด้วยการไม่บวกเวลาเผื่อกับขอบที่ผู้ใช้ยืนยันแล้ว
→ ความยาวผลลัพธ์ **ตรงกับที่สั่งเป๊ะทั้ง 7 งานที่ทดสอบ**

### 4.7 การหาจุดคอขวดด้านความเร็ว

ผู้ใช้รายงานว่างานวิเคราะห์ช้าผิดปกติ การไล่ log พบว่า **ไม่ได้มาจากฟีเจอร์ที่เพิ่งเพิ่ม**
(วิเคราะห์ภาพใช้ 2.3–14.5 วินาที · ซ่อมท่อนหลอนใช้ 13.5 วินาที) แต่มาจาก **ขนาดข้อมูลที่ส่งให้ LLM**

ระบบส่งทรานสคริปต์ทั้งโครงสร้างรวม timestamp ระดับคำไปด้วย ทั้งที่พรอมป์ไม่เคยอ้างถึงเลย

| ความยาวคลิป | ส่งจริง (ตัวอักษร) | ที่ควรส่ง | ลดลง |
|---|---|---|---|
| 11 นาที | 321,311 | 11,798 | **96.3%** |
| 7 นาที | 210,037 | 9,229 | 95.6% |
| 6 นาที | 129,704 | 4,383 | 96.6% |
| 3 นาที | 69,535 | 3,358 | 95.2% |

ผลที่เห็นใน log: คำขอเดียวใช้เวลา **160 วินาที** และเจอ HTTP 503 ติดกัน 5 ครั้ง
(คำขอที่ใหญ่เกินจำเป็นถูก throttle ง่ายกว่า) งานทั้งงานใช้ 272 วินาที
โดย **85% หมดไปกับการรอ LLM**

### 4.8 การเลือกค่าคงที่ของการวิเคราะห์ภาพ

วัดจากคลิปจริง 2 คลิป (7 นาที 60fps ตัดต่อถี่ / 11 นาที 30fps ถ่ายช็อตเดียว)

| ค่า | ตั้งที่ | เหตุผลจากการวัด |
|---|---|---|
| เกณฑ์ฉากเปลี่ยน | 15 | ที่ 10/15/20 ได้ 12.0/11.1/10.1 จุดต่อนาที — เลือกกลางช่วงที่ผลนิ่ง |
| ความยาวขั้นต่ำของจอดำ | 0.3 วิ | กรองแฟลช 0.2/0.25 วิ ทิ้ง เหลือช่วงว่างจริง 3.17 วิ |
| ความยาวขั้นต่ำของภาพค้าง | 2.0 วิ | ค่ายอดนิยม 0.5 หลวมเกิน — คลิปพูดหน้ากล้องได้ 29 ครั้งใน 7 นาที ; ที่ 2.0 เหลือ 3 |

**ข้อค้นพบเพิ่มเติม**: ค่าคะแนนของตัวตรวจจับฉากเปลี่ยน **เทียบข้ามคลิปไม่ได้**
(บังคับเฟรมเรตเป็น 15 fps แล้ว p99 กระโดดจาก 3.49 เป็น 20.61) แต่ **จำนวนจุดที่ตรวจพบเทียบได้**
(12.0 เป็น 13.4) จึงต้องตั้งเกณฑ์จากจำนวนจุด ไม่ใช่จากค่าคะแนนดิบ

## บทที่ 5 — สรุป ข้อจำกัด และข้อเสนอแนะ

### 5.1 สรุปผล

ระบบทำงานได้ครบตามวัตถุประสงค์ทั้ง 5 ข้อ วิเคราะห์ได้ทั้งเสียงและภาพตามชื่อโครงงาน
และมีส่วนติดต่อผู้ใช้ที่ให้คนตรวจสอบและแก้ไขผลของ AI ได้จริงก่อนตัดต่อ

### 5.2 ข้อค้นพบเชิงวิศวกรรม (ส่วนที่มีคุณค่าที่สุดของโครงงาน)

1. **การควบคุมพฤติกรรม LLM ด้วยพรอมป์อย่างเดียวไม่น่าเชื่อถือ** ต้องมีการตรวจสอบเชิงโครงสร้าง
   ในโค้ดที่ไม่ขึ้นกับความร่วมมือของโมเดล
2. **กลไกแก้ไขอัตโนมัติที่ทำงานบ่อยเกินไป อันตรายกว่าปัญหาที่มันแก้** กลไกที่ผูกกับ
   "เงื่อนไขที่ตรวจสอบได้" ปลอดภัย ส่วน heuristic ที่เข้าเงื่อนไขบ่อยไม่ปลอดภัย
3. **ค่าคงที่ต้องมาจากการวัดข้อมูลจริง** สมมติฐานที่ดูสมเหตุสมผลสามข้อ — Whisper segment
   เท่ากับประโยค, unique-ratio จับการวนซ้ำได้, face-crop แก้ปัญหา 9:16 ได้ — **ผิดทั้งสามข้อ**
   เมื่อนำไปวัดกับข้อมูลจริง
4. **การเลือกวิธีวัดสำคัญเท่ากับการวัด** ข้อมูลสุ่มให้ผล 67.6% ขณะที่ข้อมูลจริงให้ 1 จาก 17
5. **ออกแบบให้ความผิดพลาดเอนไปทางปลอดภัย** การถามว่า "ลบอะไร" แทน "เก็บอะไร"
   ทำให้สิ่งที่ AI ลืมถูกเก็บไว้แทนที่จะหายไป

### 5.3 ข้อจำกัดที่ทราบ

- คุณภาพขึ้นกับความชัดของเสียงต้นฉบับ เสียงที่มีดนตรีคลอหนักยังทำให้ Whisper หลอนได้
- การให้ AI เห็นภาพยังไม่ชนะทุกกรณี (ชนะชัด 1 ก้ำกึ่ง 1 จากที่ทดสอบ)
- ยังไม่มี face-aware crop สำหรับคลิปพูดหน้ากล้องที่ถ่ายมาแบบไวด์
- ประมวลผลได้ทีละงาน (worker เดียว) ไม่รองรับผู้ใช้พร้อมกันหลายคน
- ไม่มีระบบผู้ใช้หรือฐานข้อมูล เก็บงานเป็นไฟล์และลบอัตโนมัติใน 7 วัน
- ต้องพึ่ง Gemini API ภายนอก ซึ่งมีโควตาและอาจตอบ 503
- ยังไม่ได้ทดสอบเชิงปริมาณกับผู้ใช้จริงหลายคน (usability testing)

### 5.4 ข้อเสนอแนะสำหรับการพัฒนาต่อ

- เพิ่ม **face-aware crop** เป็นตัวเลือกที่สามสำหรับ 9:16 (แผนละเอียดอยู่ใน `CLAUDE.md` หัวข้อ 6.1)
- ประเมินผลเชิงปริมาณ: เปรียบเทียบเวลาที่คนตัดต่อใช้ระหว่างใช้และไม่ใช้ระบบ พร้อมวัดความพึงพอใจ
- รองรับหลายภาษาและคำบรรยายสองภาษา
- ใช้ NVENC เร่งการเรนเดอร์ (คาดว่าเร็วขึ้นประมาณ 5 เท่า)
- ขยายเป็นหลาย worker พร้อมระบบผู้ใช้ ถ้าจะนำไปใช้งานจริงกับผู้ใช้หลายคน
